## Послідовність у Postman

1. Запустити сервер, імпортувати requests/BookShelf.postman_collection.json.
2. Папка 03–04: Get CSRF та наступні 10 запитів. Cookie jar має бути увімкнений; localhost не замінювати на 127.0.0.1 посеред сесії.
3. Папка 05–06: запустити всі 10 запитів після Get CSRF. Використовують ту саму сесію, але різну Basic-авторизацію; ролі перевіряються на кожному запиті.
4. Папка 08: отримати три JWT. Вони зберігаються у змінних колекції.
5. Папка 09: виконати 10 запитів по порядку; bookId і auditId зберігаються автоматично.
6. Папка 10: виконати 5 запитів аудиту. Видалена книга залишається у журналі.

JWT закінчився або сервер перезапущено — повторити папку 08. HTTP-файли призначені для IntelliJ HTTP Client / VS Code REST Client; у них токени й ID потрібно перенести вручну.

## Скриншоти та GitHub

Скриншоти мають показувати метод, URL, відповідь і HTTP-статус. У task09 назви 01–10, у task10 — 01–05. Не публікувати чинні токени та Authorization-заголовки. GitHub поки не створений: додати власний remote і завантажити код після перевірки. Встановлені умови вимагають реальних знімків Postman/Talend та jwt.io; JUnit і текстові логи їх не замінюють.

## Межі реалізації

Аудит містить успішні CREATE/UPDATE/DELETE з іменем користувача, часом та ID книги. Логування невдалих входів чи читань не додано: у скопійованій умові цього немає. Зміни книги та її аудит зберігаються в одній транзакції. Якщо відеолекції визначають іншу модель аудиту, потрібне узгодження.

Поточний проєкт є фінальним захищеним застосунком, а не історією з десяти гілок. Незахищений проміжний варіант CRUD не запускається. Точну відповідність невідомим вимогам першого завдання та відеолекцій не підтверджено.
